# 时段权益目录

这里保存随日历时间变化的模型服务权益，以及维护时用于发现新活动的官方入口。正式收录以 `benefits/` 中的数据 JSON 为准；测试示例不代表现行优惠。

## 三类数据

- `channels/<渠道 ID>.json`：一份记录一个实际计费渠道及计费服务商；即使当前没有已记录权益，也可保留渠道。渠道身份的公开出处放在本文件。
- `benefits/<渠道 ID>/<权益 ID>.json`：一份记录一项可独立判断的时段权益。文件内的 `accessChannelId`、`id` 必须与目录和文件名一致，且直接保存支持本项权益的 `sourceReferences`。
- `discovery.json`：值得反复调查的官方文档、价目表或公告入口。它只是搜索线索，不能自动替代具体权益的证据；仍应搜索更广的一手来源。

各类文件分别遵循 `schema/` 中同名的 JSON Schema；关键字段和分支旁有自然语言说明。实际计费方优先于模型品牌归属：例如 Qoder CN 使用 Qwen 模型，不代表该活动属于阿里云百炼直连渠道。确定结论只根据实际计费方的一手公开条款维护；第三方页面可供发现，领域数据不对来源作「权威性」评分。

只为需要跨文件引用的渠道和权益保留稳定 ID：渠道及权益自身 ID 与路径一致，权益对渠道及其他权益的引用必须指向现有文件。计费方名称、内嵌日历例外和发现入口不另设孤立 ID；发现入口用 URL 去重。

## 录入和移除

一项权益需记录完整适用条件、时间条件、效果和原有计费单位。`eligibilityConditions` 同时成立才可能适用；只有来源明确覆盖该渠道所有使用情形时才用空数组。公开条款确认活动存在、却不足以精确计算时间或效果时，用相应的 `unresolved` 分支保留原文与原因，不猜测边界。来源撤回或官方材料冲突时保留记录，设 `evidenceStatus: uncertain` 并写明 `uncertaintyReason`；这不是待某个人处理的状态，也不能当成确定生效。官方明确活动结束时可删除权益文件并在 PR 留下依据；页面暂时无法访问本身不证明结束，渠道文件也无需随最后一项权益一起删除。

重复窗口的 `weekdays` 用 ISO 星期数（周一为 1）；跨午夜窗口归于开始日期。`00:00–24:00` 表示全天，`validUntil` 不含结束时点。法定假日等例外只填已由官方日历支持的年份，未来未知年份不按普通工作日推断。重叠权益仅在公开条款明确时填写组合关系；未记录关系不等于可叠加。`billingDecisionInstant` 也仅在计费方明确说明请求以何时刻判价时填写。

首版不保存逐条 `verifiedAt`，也不为复核后无变化提交时间戳 PR。Git 提交与未来目录发布时间是数据版本，不是来源核验时间。若现有 Schema 连一条活动的最小事实都无法如实保存，应提交带官方资料的「规则表达能力缺口」GitHub Issue，不在数据维护 PR 中修改 Schema；若旧确定权益已被推翻，可另提仅改旧数据的保护性 PR。

## 检查与提交

仓库根目录的 `pnpm validate:catalog` 核验当前目录的 JSON、文件名、跨文件引用及已知业务不变量；**Validate Catalog** 工作流也可手动运行，并由总检查复用。校验器不抓取网页，不判断来源是否仍有效、权威或适用于某位数据消费者。

日常数据维护 PR 使用 `catalog-update/` 分支，只修改上述三类数据 JSON；数据和 Schema、代码、文档、工作流的修改必须拆成不同 PR。自动化创建 PR／Issue 时主动填写仓库模板要求的证据与原因，不能假定 GitHub API 会自动套模板。仓库上线后，还须由管理员把目录校验和 PR 范围检查设为必需检查，才能阻止失败 PR 合并。
