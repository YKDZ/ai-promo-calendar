# 时段权益目录

这里保存实际计费渠道公开的、随政策时间变化的模型服务权益。目录是有出处的结构化政策索引，不是完整条款、个人资格判断或实际账单保证。正式收录以 `benefits/` 中的数据 JSON 为准；测试示例不代表现行优惠。

## 文件与来源

- `channels/<渠道 ID>.json`：一个实际计费渠道及其计费服务商。当前没有已记录权益时也可保留渠道；渠道身份的公开出处保存在本文件。
- `benefits/<渠道 ID>/<权益 ID>.json`：一项可独立判断的政策规则。`accessChannelId`、`id` 须与路径一致；本文件的 `sourceReferences` 直接指向支持该规则的实际计费方公开条款。
- `discovery.json`：反复调查的官方入口，只是发现线索，不能代替权益证据；仍需搜索更广的一手来源。

渠道与权益使用 `schemaVersion: 2`，发现入口仍为版本 1。各文件遵循 `schema/` 中同名 JSON Schema；字段旁的 `description` 说明录入语义。按实际计费渠道归属，不按模型研发方归属：Qoder CN 使用 Qwen 模型，不意味着 Qoder 的活动属于阿里云百炼直连渠道。第三方资料只能用于发现，不能单独支撑确定权益；领域数据不对来源打权威性分数。

稳定 ID 只用于文件身份和跨文件引用：权益引用的渠道及其他权益必须存在。计费方、模型、来源章节、日历例外和发现入口不另建 ID；发现入口按 URL 去重。

## 录入边界

一份权益文件对应一项可求值规则，不按营销页面合并。全部计费项应共享同一政策触发事件，所有列出的资格组合应共享同一实际效果；套餐、计费项或事件改变效果时拆文件。保留来源对应的模型、套餐、计费项、计价单位等简短原名，但不要在这些名称中写条件句。权益标题由消费端从结构化事实生成，JSON 不保存营销标题或通用备注。

`eligibilityConditions` 只记录模型、计费项、套餐、工具、地域、客户端、账户类型、计费模式等公共查询维度上的**必要条件**。全部条件匹配不证明某个账户最终适用；空数组只表示没有记录可计算的资格，不表示人人适用。首次付费历史、订阅状态、实际发放、余额等个人事实留给原文和账户系统，不转成任意文本谓词。`one_of.values` 放明确适用值；同一条件中只有个别值因公开资料冲突而不确定时，另放 `uncertainValues`，不要抹去其他确定值。`evidenceStatus: uncertain` 仅用于当前政策本身的来源支持无法确认，不能因为某位用户的资格未知而设置。

时间窗口只约束 `timeTrigger.kind` 指明的政策事件；类别可为模型请求、支付、领取、工具调用、持续计量、出账、订阅下单或 `unknown`。出账事件仅用于明确按出账时间判断的单项权益，不代表整个渠道如此判价；订阅下单不等于付款，类别已知也不等于判价瞬间已知。仅当计费方明确说明渠道通用的具体判价时刻时，才在渠道中填写 `billingDecisionInstant`。支付／领取窗口不等于取得后个人奖励的可用期；后者取决于账户事实，不进入目录。累计优惠用量上限等无法由静态目录求值的限制留在来源原文中；命中政策窗口不保证实际享受折扣，也不在 JSON 中另写原文转述。

尽量保留已知时间部分：每日或每周重复规则用 `recurring`，`weekdays` 是 ISO 星期数（周一为 1），跨午夜窗口归属开始日期，全天为 `00:00–24:00`。只公布开始日期、不公布该日小时的重复规则用 `validFromDate`，不能倒推首日全天适用；没有公布终止日期就不填 `validUntil`，但缺省不承诺永久有效。精确绝对边界用 `absolute`；仅公布日期而时区未知时用带 `role` 的 `knownBoundaries`，不得伪造 UTC 瞬间。已知结束时点但包含性未公布时，用 `endInclusive: null` 和 `endPrecision`。只有没有可用窗口时才用时间 `unresolved`；效果未知只影响 `effect`。法定假日等例外只填官方日历已覆盖的年份；未知年份的相关时段不能假定为普通工作日。

效果优先保存官方实际优惠单价或额度 `unit_rate`；可靠通常值才填 `regular`。通常值缺失时不能推算节省额、倍数或价格方向。仅当一个实际倍数对文件中所有情形精确成立时才用 `multiplier`；宣传月价不能替代按剩余时长折算的订单实付，无法得出统一效果时保持 `unresolved`。不同渠道同名单位不自动等价。重叠权益只有在官方明确说明且另一端已收录时才填写 `combinationRelations`；缺省不等于可叠加。

官方明确证明现行权益结束时，可删除权益文件并在 PR 写明依据；来源暂时无法访问不等于活动结束。首版不提供历史政策查询。渠道可在最后一项权益删除后继续存在。核对无变化时不改文件，也不刷新逐条核验时间戳。Git 版本不是来源核验时间。

如果 Schema 不能忠实保存活动的最小结构事实，应使用「规则表达能力缺口」GitHub Issue，附官方来源和具体缺口；不要在数据 PR 中扩展 Schema 或另造文本逃生口。若新证据同时推翻旧的确定权益，可另提只修正旧数据的保护性 PR。

## 检查与提交

根目录的 `pnpm validate:catalog` 检查 JSON、路径、跨文件引用和可机械验证的业务不变量；它不抓取网页，也不能证明资料真实、现行或适用于特定账户。新增或改变结构化事实时，在 PR 正文逐项列出字段、官方 URL 及支持该字段的页面章节；不在数据中另造字段级证据 ID。收窄或删除旧资格尤其需要完整条款或明确结束依据，搜索摘要、截断页面及一次访问失败都不够。

日常维护从最新 `main` 创建 `catalog-update/` 分支，只修改 `catalog/discovery.json`、`catalog/channels/*.json`、`catalog/benefits/<渠道 ID>/*.json`。尽量一次原子提交候选数据；推送后 GitHub 上的 **Prepare Catalog Update** 自动校验文件范围、格式与目录，并在必要时回写纯格式改动。准备成功后再创建 PR，不依赖定时维护者本地有 Git、Node 或 pnpm。数据和 Schema、代码、文档、工作流必须分 PR。

自动创建 PR／Issue 时主动填好仓库模板要求的证据，不能假定 API 会套模板。PR 还要等待 **Validate Catalog**、**Catalog PR Scope** 和 **Root Check**，准备运行不能代替合入检查；仓库管理员须将目录校验与范围检查配置为必需检查。
