# 时段权益目录

这里保存随日历时间变化的模型服务权益，以及维护时用于发现新活动的官方入口。正式收录以 `benefits/` 中的数据 JSON 为准；测试示例不代表现行优惠。

## 三类数据

- `channels/<渠道 ID>.json`：一份记录一个实际计费渠道及计费服务商；即使当前没有已记录权益，也可保留渠道。渠道身份的公开出处放在本文件。
- `benefits/<渠道 ID>/<权益 ID>.json`：一份记录一项可独立判断的时段权益。文件内的 `accessChannelId`、`id` 必须与目录和文件名一致，且直接保存支持本项权益的 `sourceReferences`。
- `discovery.json`：值得反复调查的官方文档、价目表或公告入口。它只是搜索线索，不能自动替代具体权益的证据；仍应搜索更广的一手来源。

各类文件分别遵循 `schema/` 中同名的 JSON Schema；关键字段和分支旁有自然语言说明。实际计费方优先于模型品牌归属：例如 Qoder CN 使用 Qwen 模型，不代表该活动属于阿里云百炼直连渠道。确定结论只根据实际计费方的一手公开条款维护；第三方页面可供发现，领域数据不对来源作「权威性」评分。

只为需要跨文件引用的渠道和权益保留稳定 ID：渠道及权益自身 ID 与路径一致，权益对渠道及其他权益的引用必须指向现有文件。计费方名称、内嵌日历例外和发现入口不另设孤立 ID；发现入口用 URL 去重。

## 录入和移除

一项权益需记录完整适用条件、时间条件、效果和原有计费单位。`eligibilityConditions` 同时成立才可能适用；只有来源明确覆盖该渠道所有使用情形时才用空数组。`one_of.values` 保存明确适用值；若同一资格条件只有少数值因官方资料冲突而不能确认，用同一条件的 `uncertainValues` 和 `uncertaintyReason` 局部表达，不要把整项权益的证据状态降为不确定。优先结构化已知的政策窗口：重复优惠仅有开始日期而没有小时，用 `validFromDate`；只是不知道结束瞬间是否包含，用 `endInclusive: null`、来源精度与原因，不能因此把整段时间标为 `unresolved`。只有无法结构化任何可用窗口时才用时间 `unresolved`；效果无法计算仍可单独用效果 `unresolved`。来源撤回或官方材料冲突时保留记录，设 `evidenceStatus: uncertain` 并写明 `uncertaintyReason`；这不是待某个人处理的状态，也不能当成确定生效。官方明确活动结束时可删除权益文件并在 PR 留下依据；页面暂时无法访问本身不证明结束，渠道文件也无需随最后一项权益一起删除。

一份权益文件按可求值规则拆分，不按营销活动页面合并：全部计费项必须共享同一政策触发事件，所有列出的资格组合必须共享同一可计算效果。套餐档位、计费项或触发事件导致实际效果不同时拆文件。文本资格必须是一条必要的是／否谓词；自动生效、费率解释、额度说明、组合规则和一般备注不得写入资格数组。官方同时公布实际通常费率与优惠费率时优先保存 `unit_rate`，不能用营销“几折”覆盖不满足该倍数的实际数值。

重复窗口的 `weekdays` 用 ISO 星期数（周一为 1）；跨午夜窗口归于开始日期。`00:00–24:00` 表示全天，`validUntil` 不含结束时点；未公布结束日期时留空，不表示承诺永久有效。`validFromDate` 指当地开始日内的具体时刻未知，不能倒推该日所有时段；首版不据此还原历史政策。法定假日等例外只填已由官方日历支持的年份，未来未知年份的受影响时段待核实，不因此隐藏已确定的晚间、周末等窗口。每项权益都必须填写 `timeTrigger`，指明窗口约束的是模型调用、支付、领取还是带说明的其他事件。支付／领取期不等于到账后奖励的使用期，后者依账号事实判断，不得把两者合成全局区间。来源若公开说明取得后的统一截止或相对有效期，只写入自然语言 `entitlementValidityNote`；它不参与时点求值，也不能代替时间、触发事件、资格或效果字段。不要增加或使用通用备注字段绕过结构化契约。重叠权益仅在公开条款明确时填写组合关系；未记录关系不等于可叠加。`billingDecisionInstant` 也仅在计费方明确说明请求以何时刻判价时填写。

首版不保存逐条 `verifiedAt`，也不为复核后无变化提交时间戳 PR。Git 提交与未来目录发布时间是数据版本，不是来源核验时间。若现有 Schema 连一条活动的最小事实都无法如实保存，应提交带官方资料的「规则表达能力缺口」GitHub Issue，不在数据维护 PR 中修改 Schema；若旧确定权益已被推翻，可另提仅改旧数据的保护性 PR。

## 检查与提交

仓库根目录的 `pnpm validate:catalog` 核验当前目录的 JSON、文件名、跨文件引用及已知业务不变量。**Prepare Catalog Update** 与 `check.yml` 各自在对应环境中直接运行这条命令；复用的是校验器代码和命令，而不是整份工作流。校验器不抓取网页，不判断来源是否仍有效、权威或适用于某位数据消费者。

日常数据维护从最新 `main` 创建 `catalog-update/` 分支，只修改上述三类数据 JSON，并尽量把本轮候选文件组成一次原子提交，避免逐文件推送反复触发自动化。向该分支推送后会自动运行 **Prepare Catalog Update**：它在 GitHub Runner 中核对分支与文件范围、格式化和校验目录，并在确有格式变化时把机械修正提交回原分支；人类也可用 `target_branch` 手动触发同一流程。准备成功后再创建 PR，避免依赖维护者本地是否安装 Git、Node 或 pnpm。数据和 Schema、代码、文档、工作流的修改必须拆成不同 PR。

自动化创建 PR／Issue 时主动填写仓库模板要求的证据与原因，不能假定 GitHub API 会自动套模板。PR 仍须等待 **Validate Catalog**、**Catalog PR Scope** 和 **Root Check**；准备工作流不能替代合入检查。仓库上线后，还须由管理员把目录校验和 PR 范围检查设为必需检查，才能阻止失败 PR 合并。
